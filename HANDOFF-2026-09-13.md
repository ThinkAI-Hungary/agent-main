## 1. Az ügy-sorozat (259–265) — fő funkcióváltozások

### Függő időpont-fenntartás (259-es ügy + 24 órás kiegészítés)
- A rendszer által felajánlott időpont (`confirmed_by_client=false` a Gemini JSON-ban) **ideiglenes foglalás**: `calendar_events.status='pending'` + `pending_until = +24 óra`. A naptárban halványsárga szaggatott kártya + „függőben" pill, listanézetben „Függőben" badge.
- Ügyfél egyértelmű „igen"-e → `_confirm_pending_event` ugyanazt az eseményt véglegesíti (nincs duplikátum) + visszaigazoló ICS + Lemondom CTA. Lejáratot a worker 15 percenként felszabadítja (`release_expired_pending_events`).
- **Lemondom CTA szabály**: csak a hivatalos, végleges (ICS-es) emailben + emlékeztetőben; a felajánló levélbe a beégetett 24 órás tudnivaló kerül („…24 órán keresztül tudjuk tartani…").
- Munkatárs-konzisztencia: az AI válaszlevélben SOHA nem nevez ellátót; a név egyetlen helyen oldódik meg (`event.doctor`).

### Lemondási link flow javítása (260/265)
- `/api/public/cancel`: a lemondás bejövő interakcióként naplózódik (Időpont / Törölt időpont / Lezárt) → megjelenik a naplóban és a profilban.
- **Naptár-szivárgás javítva**: a jóváhagyás-módú flow megerősítéskor `_confirm_pending_event` (nincs dupla esemény) + `_release_other_pending_events`.
- **„törölt időpont" címke**: minden lemondási útvonal az **UTÁNKÖVETÉS oszlopba** viszi az ügyfelet (nem Elveszett!) — user szabálya: minden értékesítési címkés ügyfél az első oszlopba kerül, innen csak kézzel mozgatható.

### Kritikus: időpont-módosítás idegen eseményen (265)
- `find_calendar_event_by_title` ügyfél-szűrés nélkül a legrégebbi cím-egyezést adta → a 265-ös kérelme a tulaj júniusi teszteseményét írta át. Most: a kérelmező email címére szűkített keresés (ügyfél jövőbeli → ügyfél bármely → jövőbeli bárkié → legacy), módosítás- és törlés-ágban is.

### Klasszifikációs finomítások
- **Lejárt kedvezmény-őr (260)**: a Gemini `stale_offer` jelzésnél a válasz NEM megy ki automatikusan, akció nem fut, és finomhangolási javaslat rögzül az `ai_insights`-ba („érdemes kikapcsolni vagy frissíteni").
- **Javaslati szakasz eredménye**: „Foglalási szándék rögzítve" (nem „Új időpont") — az „Új időpont" a véglegesítésre marad.
- **„járt már nálunk korábban?" tilalom** (264): három szinten (E-MAIL CSATORNASZABÁLY, VISELKEDÉSI SZABÁLYOK 5., Új ügyfél ág).
- **„Manuálisan lezárt (X)" jelölés**: a lezárás-endpoint `closed_manually=true` + `closed_by`-t ír; a `detectEredmeny` minden nézetben „Manuálisan lezárt (eredeti eredmény)" formában mutatja.

## 2. Interakciós popup — kétmódú rendszer

- **Interakciós napló (thread mód)**: összefűzött kommunikáció, „Előzmények megtekintése (N)" sáv felül (szürke, lenyitható), legutóbbi csere kibontva.
- **Ügyfélprofil / Irányítópult (single mód)**: **egy interakció = egy ügy** — a sor csak a saját váltását mutatja, NINCS előzmény.
- **`interactions.diary_fragment` oszlop**: az email flow az interakció SAJÁT napló-fragmensét menti `[ts]` fejléccel (a single mód ebből dolgozik determinisztikusan). Védőfal a régi, ts-nélküli fragmensekre + backfill.
- **Valós időpontok**: `received_at` (levél Date fejlécéből) + `sent_at` (kiküldés pillanata, autonóm + approve úton) — fejléc, lista, buborékok ezekből mutatnak.
- Kimenő kommunikáció: csak a kiküldött üzenet (tárgy a fejléc-címke). Tárgy sor az email-buborék felett. Kiküldés után a választerv eltűnik; a ténylegesen kiküldött (esetleg szerkesztett) szöveg a szürke blokkban látszik (a rekord frissül az approve-ban).
- Design: fehér fejléc + kit-07 csatorna-chip, türkiz ÖSSZEFOGLALÁS kártya fix magassággal + belső scroll, Státusz/Teendő szürke kártyák, pending választerv ea-logóval + türkiz buborék + Szerkesztés/Jóváhagyás és elküldés gombok.
- Messenger/Instagram 24h: banner helyett „24 órás válaszablak" modal (Értem, localStorage).

## 3. Olvasottság-rendszer + Értesítési központ redesign

- **`read_interaction_ids` (localStorage)**: sor-kattintásra az interakció elolvasott lesz; kis kék pötty a sor elé a naplóban és az irányítópulton. Per-böngészős olvasottság (csapatszintű olvasottság = külön tétel, DB háttér kell).
- **Értesítési központ**: a bell az OLVASATLAN bejövő interakciókat mutatja (közös tároló — a naplóban olvasott eltűnik innen is), érkezési sorrendben felül a legújabbal; badge = olvasatlanok száma. Sor: csatorna-tile + ügyfélnév + „csatorna · ügytípus" (determinisztikus) + státusz-pötty (Sürgős/Nyitott/Lezárt) + időpont. ## 6. Tanulságok (rögzítve a HANDOFF.md-ben is)

| Tanulság | Részlet |
|---|---|
| **`useBlocker` csak data-routerrel működik** | a `<BrowserRouter>` appot eldobta → a kilépés-modal beforeunloadra korlátozódik (`7971e3a`) |
| **TDZ/deklaráció-sorrend** | az optimista lezárás deklarációja a használat UTÁN volt → ReferenceError (`f36ed06`) |
| **`check_imap_sync` vs. tenant-path** | a Date fejléc parse a rossz függvénybe került → minden email NameError (`a4038f7`) |
| **Supabase MCP default projekt ≠ staging** | az MCP a dsiluafthysysnstszbd-re mutat (élő), a staging qhhnqqsthdrwacsxommt — Management API-val migrálni kell |
| **Lemez-takarítás** | a 24 GB-os lemez megtelt docker build-cache-mel (~14 GB prune kellett) — periodikus prune szabály |
| **useSessions mezőtükör** | új interactions-oszlopnál a hook explicit mezőlistáját is frissíteni kell |
| **Fragment = `[ts]` fejléc** | a log_szoveg-hez az időbélyeget a diary-append adja, nem a fragment — parse 0 blokk nélküle |
